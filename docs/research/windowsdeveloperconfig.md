# 调研笔记：microsoft/WindowsDeveloperConfig

> 调研日期：2026-10-19
> 调研对象：https://github.com/microsoft/WindowsDeveloperConfig
> 调研方式：一手来源为主 —— GitHub 仓库本身（main 分支文件、提交历史、分支列表）与 Microsoft Learn 官方文档（WinGet Configuration / DSC / Dev Home）。二手资料未作为论断依据。

## 概述

**microsoft/WindowsDeveloperConfig** 是微软官方的 Windows 开发环境自动化配置仓库（MIT 许可，仓库创建于 2026-05-21，截至调研日约 3.1k stars、219 forks、252 commits）。仓库自我定位是 "Opinionated setups for Windows dev boxes. Idempotent. CI-tested."（有主见的开发机配置方案，幂等、经 CI 测试），口号是 "Set up a new Windows dev box in minutes, not hours."（见[根 README](https://github.com/microsoft/WindowsDeveloperConfig/blob/main/README.md)）。

仓库提供四条主流程（根 README「Pick your setup」一节）：

1. **Windows Dev Config**（整装机）：装工具 + 改 Windows 设置 + WSL/Ubuntu + 终端定制，一条命令、一次重启。
2. **WSL Comfort**：打磨 Windows + WSL 的 shell 体验（zsh/bash、Starship、现代 CLI 工具、主题化终端）。
3. **Workloads**：单语言/单工具链安装（TypeScript、Java、Python、SQL、PowerShell、.NET、Go、Rust、PHP、WinUI 3、WinForms、WinAppCLI）。
4. **AI tooling**：检测 GPU 并安装匹配的 PyTorch 构建（CUDA/ROCm/Intel XPU/CPU），可选 Ollama、llama.cpp、Foundry Local。

**一个关键的历史事实（影响对全部调研问题的回答）**：该仓库的机制在 2026 年内发生过一次大迁移。仓库最初的形态（首日提交 `0b99d3503d`，2026-05-21）是**纯 winget configure + PowerShell DSC**：一个 [`Windows Dev Config/dev-config.winget`](https://github.com/microsoft/WindowsDeveloperConfig/blob/0b99d3503d/Windows%20Dev%20Config/dev-config.winget) 单文件声明整台开发机，外加每语言一个 `configuration.winget`。而当前 main 分支的主体（Windows Dev Config、大部分 Workloads）已迁移为 **PowerShell 原生引擎**（`dev-config.ps1` + 步骤/阶段脚本），CI workflow 里的注释直接说明了这一点："migrates workloads from the winget-configure/DSC model to a PowerShell-native engine (windows-dev-config/dev-config.ps1 + Workloads/<name>/setup.ps1)"（见 [`.github/workflows/ci.yml`](https://github.com/microsoft/WindowsDeveloperConfig/blob/main/.github/workflows/ci.yml)）。仅剩 5 个语言工作流（TypeScript/Java/Python/SQL/PowerShell）仍以声明式 `configuration.winget`（winget configure）为主载体。

## 仓库结构

### 目录组织：`src/` 真源 + 顶层签名副本

仓库最重要的结构约定（根 README「Note on the repo layout」原话）：

> the `src/` tree is the source of truth. The top-level `windows-dev-config/`, `Workloads/`, and `wsl-comfort/` folders are Authenticode-signed release copies regenerated by the sign pipeline, so please don't edit them directly.

即：**贡献者/定制者只改 `src/`；顶层三个目录（`Workloads/`、`windows-dev-config/`、`wsl-comfort/`）是签名流水线（`.pipelines/OneBranch.SignAndPackage.yml`）再生成的 Authenticode 签名发布副本**。PR 上有 "Signed copy guard" 检查（`.github/workflows/signed-copy-guard.yml` + `src/tools/check-signed-drift.ps1`），比较顶层签名副本与 `src/` 的漂移（见 [src/docs/development.md](https://github.com/microsoft/WindowsDeveloperConfig/blob/main/src/docs/development.md)）。

主要目录及其职责（依据 [main 分支完整文件树](https://api.github.com/repos/microsoft/WindowsDeveloperConfig/git/trees/main?recursive=1) 与 [src/docs/windows-dev-config.md](https://github.com/microsoft/WindowsDeveloperConfig/blob/main/src/docs/windows-dev-config.md) 的 File layout 表）：

| 路径 | 职责 |
| --- | --- |
| `src/manifest.yml` | 「Single source of truth for every flow」：每个流程的 id、安装入口、`configuration.winget` 路径、hello-world 的 build/run/expected、UX 元数据；CI 矩阵、Command Palette 扩展、各流程 shim 都读它 |
| `src/windows-dev-config/` | 整装机引擎：`bootstrap.ps1`（远程入口：提权、校验下载、受保护安装）、`dev-config.ps1`（共享编排器：提权/shell 选择/运行锁/日志/阶段/汇总）、`setup-*.ps1`（固定动作包装）、`steps/<phase>.ps1`（每阶段一个文件）、`workloads/<name>.ps1`（工作负载定义）、`uninstall.ps1` |

| `src/future/cmdpal/QuickWingetSetup/` | PowerToys Command Palette 扩展（C#，按 manifest 渲染可运行条目） |

### 每个配置方向各覆盖什么

**（a）整装机（windows-dev-config，内部代号 Calm OS / calm-os）**——11 个阶段按序执行（[src/docs/windows-dev-config.md](https://github.com/microsoft/WindowsDeveloperConfig/blob/main/src/docs/windows-dev-config.md)「The phases」）：Getting ready → Packages → System settings → File Explorer → Taskbar/search/start → Edge → Fonts → Windows Terminal → PowerShell profile → GitHub Copilot（best-effort）→ WSL + Ubuntu。覆盖内容（[windows-dev-config/README.md](https://github.com/microsoft/WindowsDeveloperConfig/blob/main/windows-dev-config/README.md)）：

- **Windows 设置**（README 的 registry 表，逐键列出）：系统级（Sudo 内联模式、开发者模式、Win32 长路径、允许远程桌面）、资源管理器（显示扩展名/隐藏文件/标题栏全路径/打开到"此电脑"、关闭常用/最近/推荐/云文件/同步提示）、任务栏与开始/搜索（全局勿扰、隐藏蓝牙托盘、右键结束任务、搜索无 Web 结果、无搜索高亮、无开始推荐/账户通知、关闭小组件）、Edge 策略（空白新标签页、跳过首启体验）、深色主题（应用+系统）。
- **终端与字体**：PowerShell 7 设为 Terminal 默认 profile；Cascadia Code/Mono NF 字体（pin 在 cascadia-code `2407.24` 发布、SHA-256 校验、全机安装）；Oh My Posh 写入 `$PROFILE`；新增 GitHub Copilot Terminal profile（以 settings fragment 方式）。
- **WSL**：`wsl --install --no-distribution`（或回退 dism 启用 VirtualMachinePlatform + WSL 功能）→ 重启 → `wsl --install -d Ubuntu --no-launch`。发行版内不配置任何东西（那是 WSL Comfort 的职责）。

**（b）单语言 Workloads**（覆盖面见 [src/manifest.yml](https://github.com/microsoft/WindowsDeveloperConfig/blob/main/src/manifest.yml) 各 flow 的 description）：

- 声明式（`configuration.winget`）：**TypeScript**（Node.js LTS + 全局 tsc）、**Java**（Microsoft Build of OpenJDK 25 LTS）、**Python**（CPython 3.14 + uv）、**SQL**（SQL Server Developer + sqlcmd + VS Code SQL 数据库项目扩展）、**PowerShell**（pwsh 7 + VS Code PowerShell/Pester 扩展 + PSScriptAnalyzer 规则配置）。
- PowerShell 原生（`setup.ps1` 调引擎）：**.NET**（.NET 10 SDK）、**Go**、**Rust**（rustup + VS Community 的 C++ 桌面工作负载）、**PHP**、**WinUI 3**、**WinForms**、**WinAppCLI**（开发者模式 + .NET 10 + Windows App CLI）。

**（c）AI 工作负载**：PyTorch（按硬件选 CUDA/ROCm/XPU/CPU 构建）、CUDA、ROCm/HIP、Intel AI（OpenVINO/SYCL）、Ollama、llama.cpp、Foundry Local，以及 `local-ai` 汇总场景。

**（d）WSL Comfort**（[wsl-comfort/readme.md](https://github.com/microsoft/WindowsDeveloperConfig/blob/main/wsl-comfort/readme.md)）：WSL + Ubuntu、默认 zsh（可选 bash）、Starship 提示符、约 12 个 apt CLI 工具（fzf/ripgrep/fd-find/bat/jq/eza/btop/tmux）、Homebrew（gh/direnv/zoxide）、剪贴板与 `open` shim、托管式 dotfile 块、Git 默认值（`init.defaultBranch=main` 等）、Nerd Font、主题化 Terminal profile。

> **澄清调研问题中的一个预设**：本仓库**从未**有过 "VisualStudio.dsc.yaml / vscode.dsc.yaml / powershell.dsc.yaml" 这类按方向拆分的配置文件。从首个提交起就是「一个整机 `dev-config.winget` + 每语言一个 `configuration.winget`」。那种按方向拆分的样例形态存在于姊妹仓库 [microsoft/winget-dsc](https://github.com/microsoft/winget-dsc/tree/main/samples)（即 Learn 文档 FAQ 里 aka.ms/dsc.yaml 指向的样本库，已用 curl 验证 301 重定向），不在本仓库范围内。Visual Studio / VSCode / Terminal / PowerShell 等方向在本仓库中的对应物分别是 `steps/visual-studio.ps1`、`Microsoft.VSCode.Dsc/VSCodeExtension` 资源、`steps/terminal.ps1`、`steps/powershell-profile.ps1`。

## 机制原理

### WinGet Configuration 与 PowerShell DSC 的关系

Learn 官方定义（[WinGet Configuration](https://learn.microsoft.com/en-us/windows/package-manager/configuration)）：WinGet Configuration = **YAML 格式的配置文件**（列出软件、版本、工具与设置的目标状态）+ **PowerShell DSC**（执行自动化）+ **`winget configure` 命令**（发起配置）。它是声明式的：文件描述"期望状态"而非命令序列；winget 解析校验文件后，下载所需的 PowerShell 模块（内含 DSC 资源），用户确认可信后开始 Test/Set 各资源。资源顺序无关，可用 `dependsOn` 声明依赖；个别资源失败不会中断整个配置。

底层引擎是 **DSC v3**（[Microsoft Desired State Configuration overview](https://learn.microsoft.com/en-us/powershell/dsc/overview?view=dsc-3.0)）：独立 CLI `dsc`，不依赖 PowerShell 本体、无 LCM 服务、配置文档用 JSON/YAML 定义；通过 `Microsoft.DSC/PowerShell`、`Microsoft.Windows/WindowsPowerShell` 等**适配器资源**兼容旧 PSDSC 资源。Learn 明确列出 WinGet 是 DSC v3 的早期集成方之一（"Higher order tools, like WinGet, Microsoft Dev Box, and Azure Machine Configuration are early partners for DSC as orchestration agents"）。

本仓库当前的 `configuration.winget` 文件走的就是 **dscv3 处理器路径**。以 [Workloads/python/configuration.winget](https://github.com/microsoft/WindowsDeveloperConfig/blob/main/Workloads/python/configuration.winget) 为例（原文照录结构）：

```yaml
$schema: https://raw.githubusercontent.com/PowerShell/DSC/main/schemas/2023/08/config/document.json
metadata:
  winget:
    processor: dscv3
resources:
  - name: Python
    type: Microsoft.WinGet/Package
    properties:
      id: Python.Python.3.14
      source: winget
      acceptAgreements: true
    metadata:
      winget:
        securityContext: elevated
```

仓库中出现过的 DSC 资源类型（一手来源：[python](https://github.com/microsoft/WindowsDeveloperConfig/blob/main/Workloads/python/configuration.winget)、[typescript](https://github.com/microsoft/WindowsDeveloperConfig/blob/main/Workloads/typescript/configuration.winget)、[powershell](https://github.com/microsoft/WindowsDeveloperConfig/blob/main/Workloads/powershell/configuration.winget) 三个现行配置 + 初始 [`dev-config.winget`](https://github.com/microsoft/WindowsDeveloperConfig/blob/0b99d3503d/Windows%20Dev%20Config/dev-config.winget)）：

| 资源类型 | 用途 |
| --- | --- |
| `Microsoft.WinGet/Package` | 按 winget 包 id 安装（`id`/`source: winget`/`acceptAgreements`） |
| `Microsoft.Windows/Registry` | 声明注册表键值（`keyPath`/`valueName`/`valueData.{DWord:String:...}`/`_exist`） |
| `Microsoft.DSC.Transitional/RunCommandOnSet` | Set 阶段执行外部命令（如 npm 全局装 tsc、改 Terminal settings.json） |
| `Microsoft.DSC.Transitional/PowerShellScript` / `WindowsPowerShellScript` | get/test/set 三段式 PowerShell 脚本资源（WSL 安装/重启/装 Ubuntu 用它实现） |
| `Microsoft.VSCode.Dsc/VSCodeExtension` | 装 VS Code 扩展（`Name: ms-vscode.powershell` + `Exist: true`） |

Learn 的编写指南（[How to author a WinGet Configuration file](https://learn.microsoft.com/en-us/windows/package-manager/configuration/create)）还给出官方示例中的资源类型：`Microsoft.Windows.Developer/OsVersion`（断言最低 OS 版本）、`Microsoft.Windows.Settings/WindowsSettings`（如 `DeveloperMode: true`）、`Microsoft.WinGet.DSC/WinGetPackage`（v2 旧名）、`Microsoft.VisualStudio.DSC/VSComponents`（从 `.vsconfig` 装 VS 工作负载）。

### YAML schema：两代格式

**注意：配置 schema 不在 winget-pkgs 仓库**（调研问题里的预设需要修正）。官方 schema 短链 `https://aka.ms/configuration-dsc-schema/` 实际 301 指向 **microsoft/winget-cli** 仓库的 [`schemas/JSON/configuration/configuration.schema.0.2.json`](https://github.com/microsoft/winget-cli/blob/master/schemas/JSON/configuration/configuration.schema.0.2.json)（已用 curl 验证；HTTP 200）。这是 winget 自有的 "configurationVersion 0.2" 格式：根节点 `properties`，下分 `assertions` 与 `resources`，每项资源用 `resource: {模块}/{资源}`、`directives`（`description`/`allowPrerelease`/`securityContext`）、`settings`。

本仓库现行文件用的是 **DSC v3 文档 schema**（`$schema` 直接指向 [PowerShell/DSC 仓库的 document.json](https://raw.githubusercontent.com/PowerShell/DSC/main/schemas/2023/08/config/document.json)，同样验证 200）：根节点为 `resources`（每项 `type`/`name`/`properties`/`dependsOn`/`metadata`），elevation 声明挪到 `metadata.winget.securityContext`。

**文件命名约定**（Learn create 指南）：扩展名用 `.winget`（如 `configuration.winget`）；Git 项目默认放 `./.config/configuration.winget`。文件第一行建议加 `# yaml-language-server: $schema=...` 注释以便 VS Code YAML 扩展校验。两个版本共用的变量：`${WinGetConfigRoot}` 表示 `winget configure` 的执行目录，可用来拼相对路径。

### 如何应用一份配置

四条官方/仓库路径（均为一手来源）：

1. **命令行 `winget configure`**（[configure 命令参考](https://learn.microsoft.com/en-us/windows/package-manager/winget/configure)）：`winget configure -f <file>`。前提：Windows 10 1809（17763）+ 或 Windows 11，winget **v1.6.2631+**。常用旗标：`--accept-configuration-agreements`（跳过交互确认）、`--disable-interactivity`、`--module-path`、`--processor-path`、`--wait`、`--verbose-logs`、`--proxy`。子命令：`show`（展示文件详情）、`list`（列出已应用配置）、**`test`**（对照配置检查系统、不改动）、**`validate`**（只校验文件）、`export`（导出为配置）。别名：`configuration`、`dsc`。
2. **资源管理器双击**（Learn 主文档："download the configuration file and double-click to invoke the configuration"）。
3. **Dev Home GUI**：曾是官方图形入口（Machine configuration 工具可选择 WinGet Configuration 文件），但 **Dev Home 自 2025 年 5 月起不再作为 Windows 11 功能受支持**（Learn 归档页原话："Starting May 2025, Dev Home will no longer be supported as a feature in Windows 11"，见 [Dev Home（previous versions）](https://learn.microsoft.com/en-us/previous-versions/windows/dev-home/)）。即 GUI 路线已经退役，`winget configure` 命令行是现行主路径——这也解释了本仓库为什么把入口做成 PowerShell 一行命令。
4. **本仓库的 IRM 一行命令**（根 README）：`irm https://aka.ms/devconfig/standard/setup.ps1 | iex` 等。已用 curl 逐一验证重定向：`aka.ms/devconfig/standard/setup.ps1` → `raw.githubusercontent.com/microsoft/WindowsDeveloperConfig/refs/heads/main/windows-dev-config/setup-standard.ps1`；`aka.ms/devconfig/local-ai/setup.ps1` → `Workloads/local-ai/setup.ps1`（301）。入口脚本下载签名 bootstrap → 校验签名 → 安装到 `%ProgramData%\CalmOS` → 运行。对 5 个声明式语言工作流，从克隆运行的方式是（根 README 原文）：`winget configure -f .\Workloads\typescript\configuration.winget --accept-configuration-agreements --disable-interactivity`。

仓库的胶水层（[Workloads/_common/apply-configuration.ps1](https://github.com/microsoft/WindowsDeveloperConfig/blob/main/Workloads/_common/apply-configuration.ps1)）固定传 `--accept-configuration-agreements --disable-interactivity`，且注释明确指出：**`--accept-package-agreements` 不是 `winget configure` 的合法旗标**（只属于 `winget install`），包协议同意由 `--accept-configuration-agreements` 覆盖。

### 前置条件与开关

- `winget configure` 可能需要先启用：官方修复路径是 **`winget configure --enable`**（需要商店访问）+ 安装 `Microsoft.VCRedist.2015+.x64`（configure 路径的传递依赖）。见 [Workloads/_common/enable-winget-configure.ps1](https://github.com/microsoft/WindowsDeveloperConfig/blob/main/Workloads/_common/enable-winget-configure.ps1) 与 [assert-winget-configure.ps1](https://github.com/microsoft/WindowsDeveloperConfig/blob/main/Workloads/_common/assert-winget-configure.ps1)。
- 组策略可禁用：ADMX `EnableWindowsPackageManagerConfiguration`（`HKLM\SOFTWARE\Policies\Microsoft\Windows\AppInstaller`，0 = 禁用）。Learn 主文档 FAQ 与 assert 脚本一致。
- 无交互会话（SSH 无桌面、计划任务）可能无法启动 AppInstaller COM 服务器 —— assert 脚本列为已知失败模式。

## 定制与扩展点

### fork 后改哪里：官方「Customizing it」表

[windows-dev-config/README.md](https://github.com/microsoft/WindowsDeveloperConfig/blob/main/windows-dev-config/README.md) 有专门一节 "Customizing it"，开门见山："Edit the files under `src\windows-dev-config` in your clone, then run the unsigned-source command." 官方定制对照表：

| 想做什么 | 改哪里 |
| --- | --- |
| 增删软件包 | 加进 `steps/packages.ps1` 的包目录，然后在 `workloads/devconfig.ps1` 的 packages 阶段清单里列出/移除其名字 |
| 改/删某条 Windows 设置 | 对应 `steps/registry-*.ps1` 里的共享 `$tweaks` 列表 |
| 完全跳过 Edge 策略 | 从 `workloads/devconfig.ps1` 的阶段清单里删掉 `edge.ps1` 条目 |
| 不开远程桌面 | 删 `steps/registry-system.ps1` 里的 `RemoteDesktop` 条目 |
| 换终端字体 | `steps/fonts.ps1` 的 `$Script:CascadiaDefaultFontFace` |
| 换发行版 | `steps/wsl.ps1` 的 `$Script:DevConfigWslDistributionName` |
| 加新东西 | 照抄任一阶段文件的形状：用 `New-DevConfigStep` 构造步骤、交给 `Invoke-DevConfigSteps` |
| 加单工作负载 | 见 "Adding a workload"（下述四步） |

阶段（phase）= 一个文件 + 工作负载阶段清单里的一条；`_` 前缀文件是共享助手不是阶段。安装与卸载共用同一批阶段文件（`Uninstall = $true` 的阶段提供清理；包条目用 `KeepOnUninstall`/`AdditionalUninstallIds`/`UninstallOrder`/`InnoUninstall` 控制卸载差异；注册表项默认重置）。

### 加一个引擎工作负载（[src/docs/windows-dev-config.md](https://github.com/microsoft/WindowsDeveloperConfig/blob/main/src/docs/windows-dev-config.md) "Adding a workload"）

1. 加 `workloads/<name>.ps1`：返回 hashtable（`Name`/`Actions`/`Phases` 必填，每阶段 `File`+`Function`+`Title`，可选 `Parameters`/`Steps`/`MinimumOSVersion` 等），不得改机器；照抄 `workloads/winui.ps1`。
2. 尽量复用阶段；装包走 packages 阶段（新包先进 `steps/packages.ps1` 目录一次，所有工作负载即可引用）；可用 `Steps` 从共享阶段挑个别步骤（WinUI 对开发者模式和 WinUI 模板就是这么干的）；只有全新工作才写新阶段文件（如 `steps/visual-studio.ps1`）。
3. 在 `src/Workloads/<name>/setup.ps1` 加签名入口（复制 winui 的，只改 `-Workload`）。
4. 免签名测试：`.\src\windows-dev-config\dev-config.ps1 -AllowUnsigned -Workload <name>`。

### 加一个声明式（DSC）语言流程（[src/docs/development.md](https://github.com/microsoft/WindowsDeveloperConfig/blob/main/src/docs/development.md)）

官方说法是「**一次数据变更，不是流程变更**」：加一个 `configuration.winget` + 一个以 `INSTALL_OK: <lang>` 结尾的薄 `install.ps1` shim + 一个带 `expected.txt` 的 hello-world 测试 + 一条 `manifest.yml` 条目。CI 不用改。

### VS / VSCode / Git / Terminal / WSL / 开发者模式分别如何声明

- **Visual Studio**（PowerShell 原生路线，[steps/visual-studio.ps1](https://github.com/microsoft/WindowsDeveloperConfig/blob/main/src/windows-dev-config/steps/visual-studio.ps1)）：目标锁定 **VS Community 2026**（产品 `Microsoft.VisualStudio.Product.Community`，版本域 `[18.0,19.0)`，与 packages.ps1 中的 `Microsoft.VisualStudio.Community` winget 包对应）；用 `vswhere -requires <组件id>` 检测、用 VS Installer（setup.exe）增补工作负载/组件，处理 1641/3010/862968 需重启退出码。声明式路线的官方写法（Learn create 指南示例）：`Microsoft.VisualStudio.DSC/VSComponents` 资源 + `${WinGetConfigRoot}\..\.vsconfig` + `includeRecommended: true`。
- **VSCode**：包本体 `Microsoft.WinGet/Package`（`Microsoft.VisualStudioCode`）；扩展用 `Microsoft.VSCode.Dsc/VSCodeExtension`（`Name: ms-vscode.powershell`、`Exist: true`，见 [Workloads/powershell/configuration.winget](https://github.com/microsoft/WindowsDeveloperConfig/blob/main/Workloads/powershell/configuration.winget)）。
- **Git**：引擎里就是包目录中的 `Git.Git`（含 Inno 卸载器元数据）；DSC 路线为 `Microsoft.WinGet/Package` + `id: Git.Git`（初始 dev-config.winget 即如此）。注意引擎 README 的已知限制明确："Git and GitHub CLI are installed, not configured"——不做 `git config` 用户身份。
- **Windows Terminal**：引擎用 `steps/terminal.ps1`（默认 profile、`settings.json.bak` 备份、settings fragment 加 Copilot profile）；DSC 路线用 `Microsoft.DSC.Transitional/RunCommandOnSet` 跑 PowerShell 改 `settings.json`（初始 dev-config.winget 的 `ps7default` 资源）。
- **WSL**：引擎 `steps/wsl.ps1`（`wsl --install` → 重启 → 计划任务续跑 → 装 Ubuntu）；DSC 路线用三段式 `WindowsPowerShellScript` 资源链（InstallWslComponents → RebootForVmp（写 RunOnce 续跑键再强制失败让 DSC 停下）→ InstallUbuntu），见初始 dev-config.winget。
- **开发者模式**：引擎写在 `steps/registry-system.ps1`（`HKLM\...\AppModelUnlock\AllowDevelopmentWithoutDevLicense=1`）；DSC 路线两条官方写法——`Microsoft.Windows/Registry` 直接写键（本仓库初始文件，注释说它替代 Settings 资源）或 `Microsoft.Windows.Settings/WindowsSettings` 的 `DeveloperMode: true`（Learn 示例）。
- **wsl-comfort 定制**（其 readme "Customization"）：apt 包清单改 `comfort-shell-bootstrap.sh` 顶部两个数组；提示符改 `install_prompt` 的 write_file 块（或 `INSTALL_PROMPT="no"` 自带）；终端主题/字体改 `install.ps1` 的 `Install-TerminalProfile`（配色内联）。

## 应用与验证

### 在一台机器上运行

- **免克隆一行命令**（面向最终用户，根 README）：`irm https://aka.ms/devconfig/standard/setup.ps1 | iex`（标准）、`.../full/setup.ps1`（完整）、`.../standard/uninstall.ps1`（卸载）、`.../wsl-comfort/setup.ps1`、`.../local-ai/setup.ps1`、各单工作负载 `.../<name>/setup.ps1`。aka.ms 均指向本仓库 main 的 raw 文件（已验证）。
- **从克隆运行未签名源码**（面向 fork/定制者，README "Running it other ways"）：`powershell.exe -NoProfile -File .\src\windows-dev-config\dev-config.ps1 -AllowUnsigned`（`-AllowUnsigned` 选中 `src/` 树并跳过签名校验；官方建议测试机上先 `Set-ExecutionPolicy -Scope CurrentUser Bypass`）。
- **参数面**（`dev-config.ps1`/`bootstrap.ps1` 的 param 块，一手核对）：`-Action Full|Partial|Uninstall`、`-Workload <name>`、`-Scenario <ai场景>`、`-Ref <branch|tag|40位SHA>`（bootstrap 经 Git ref 解析把下载 pin 到同一提交；短 SHA 不支持）、`-AllowUnsigned`、`-NoLaunch`（只装不跑）、`-InstallRoot`（改安装目录）、`-NoElevate`、AI 系 `-PlanOnly`/`-ReportRoot`/`-AiBackend`/`-AiRuntime`/`-RequireTriton`。
- **声明式流程**：`winget configure -f <file>`（或双击）。

### 权限要求

- 引擎：**需要管理员**（README Requirements：Administrator rights + 两次 UAC；HKLM 设置、WSL 功能、全机装包都要）。运行锁 `Global\WindowsDevConfigSetup` 防并发；WSL 需硬件虚拟化（BIOS VT-x/AMD-V 或嵌套虚拟化），会自动重启一次并用计划任务 `WindowsDevConfigResume` 在下次登录后续跑（只重启一次，绝不循环）。
- DSC：资源级 `securityContext: elevated`（旧格式在 `directives` 下）→ Learn 原话："WinGet will prompt for one UAC approval at the start of the configuration. WinGet will then launch two processes: one that runs resources with elevated privileges and another that runs resources with the current user's privileges."
- Learn 故障排查提示：配置失败最常见原因是某 DSC 资源需要管理员权限。

### 验证与"预览"

- **`winget configure validate`**（只验文件）与 **`winget configure test`**（对照配置检查系统当前是否合规、**不改动**）是官方提供的非破坏性检查（[configure 参考](https://learn.microsoft.com/en-us/windows/package-manager/winget/configure)）。仓库开发流程也把它纳入：development.md 的本地测试步骤第 2 条即 "`winget configure test` to validate DSC without applying"。
- **引擎没有 -WhatIf/dry-run**。README「Known limitations」表格明确两行："No package selection at run time"（Full/Partial 装全部包，无 -Skip）与 "**No dry run** — There's no -WhatIf. The `already OK` output tells you what a re-run *would* skip, but only after the fact."（重跑时步骤先 check 后 apply 再 check，`already OK` 表示未动任何东西——这是事后而非事前预览）。
- **幂等与验证闭环**：每步 check→apply→verify；CI 对每个流程执行「装 → build/run hello-world → 输出与 expected.txt 比对 → 重跑证明幂等」（ci.yml 顶部注释 + development.md）。AI 场景用 `-PlanOnly` 出 JSON 计划报告（schema 见 `src/docs/ai-workload-report.schema.json`）。
- **日志**：`%ProgramData%\CalmOS\devconfig-log.txt`（单工作负载 `<workload>-log.txt`）；汇总报告变更数/已达标数/被 flag 的 best-effort 步骤。
- **免装机的自检脚本**（贡献者指南）：`src\tests\calm-os\` 下的 module-path-checks / winget-source-checks / pwsh-discovery-checks / wsl-query-checks 可在不动机器的情况下检查引擎行为。

## 与上游同步

**官方没有发布「个人 fork 维护指南」。** 一手来源里与此相关的全部内容是：

1. 根 README / CONTRIBUTING.md 面向的是**向上游贡献**（Fork 按钮 → 改 `src/` → PR），CONTRIBUTING.md 原文指向 "Source is under `src/`"+ `src/docs/development.md`，没有任何「fork 后如何长期跟上游」的章节。
2. 面向**使用者**的官方主张恰恰是"无需克隆"：脚本被下载、签名、校验后运行（根 README "Nothing to clone"）。
3. 与同步相关的既有机制（可作为个人 fork 策略的积木）：
   - **`-Ref` 钉版本**：bootstrap 支持 branch/tag/commit-SHA，可把一次运行钉在上游某提交（README "Pin a tag, or try a branch"）。发布机制是两段式提交签名（development.md/windows-dev-config.md「Publishing a release」：payload 签名提交 A → 启动器引用 A 的完整 SHA 并签名提交 B），aka.ms 短链永远指向 main 上的启动器。
   - **Signed copy guard**：若 fork 者直接改顶层签名副本，PR 检查会报与 `src/` 的漂移——所以 fork 中的变更应集中在 `src/`，让顶层副本保持"纯上游"可快进合并；或者干脆接受漂移、在 fork 里关掉该检查。
   - 仓库尚无 tag/Release，"跟上游"实际就是跟 main 的常规 git 合并（`git remote add upstream … && git fetch upstream && git merge/rebase upstream/main`），冲突面集中在 `src/windows-dev-config/steps/*` 与 `src/manifest.yml`。
   - 删除文件要同时动两棵树（development.md：签名流水线只增不删，`src/` 删掉的文件会残留在顶层）——fork 清理时注意。

## 对「个人定制 fork」的启示（面向基于它定制个人 Windows 开发环境）

1. **先选定制层次，别急着 fork 全仓库。**三条路线成本递增：
   - **自写 `configuration.winget`（最轻）**：如果目标只是"装一组软件 + 少量设置"，参考本仓库 5 个语言配置 + Learn create 指南，几十行 YAML 即可，用 `winget configure validate`/`test` 免费获得校验与预检。`Microsoft.WinGet/Package`、`Microsoft.Windows/Registry`、`Microsoft.VSCode.Dsc/VSCodeExtension` 三个资源类型已覆盖个人定制的大部分需求。
   - **复用引擎 + 改目录（推荐）**：fork 后只动 `src/windows-dev-config/steps/packages.ps1`（包目录）、`steps/registry-*.ps1`（`$tweaks`）、`workloads/devconfig.ps1`（阶段/包清单），即可得到「官方引擎的全部工程能力（幂等、重试、重启续跑、日志、卸载）+ 完全个人的清单」。这正是官方 "Customizing it" 表设计的用法。
   - **写个人工作负载**：加 `workloads/<me>.ps1`（照抄 `winui.ps1`），不动 `devconfig`，可与官方工作负载并存。
2. **签名体系决定了 fork 的运行方式**：fork 里的文件没有微软 Authenticode 签名，签名副本机制对你失效，必须走 `dev-config.ps1 -AllowUnsigned`（README 明示 `-AllowUnsigned` selects `src/windows-dev-config/` and skips signature checks）。个人机器上这没有安全损失（代码本来就是你自己审过的），但意味着 fork 的正确姿势是**只用 `src/` 树 + clone 运行**，不要试图复刻 aka.ms/irm 分发链。
3. **为可合并而设计**：改动尽量做成「目录里加一行/清单里加一条」的形态（包、注册表 tweak、阶段条目），避免重写官方步骤文件函数体——上游最活跃的变更恰好集中在这批 steps 文件。`manifest.yml` 若加流程必须同步（CI/CmdPal/shim 都读它）。
4. **拿掉/改掉与你偏好冲突的"有主见"默认值**（README Known limitations 列出的反直觉点）：Remote Desktop 被打开（`registry-system.ps1` 删 `RemoteDesktop`）、全局勿扰、两条 Edge 策略（会导致 Edge 显示"由组织管理"，跳过则删阶段清单里的 `edge.ps1`）、Node LTS 与 nvm 同时安装（要 nvm 管理就先卸 Node）、卸载是破坏性的（会删 Ubuntu 数据且不恢复先前设置）。
5. **验收手段现成**：每步 check/apply/verify + `already OK` 语义 + 重跑即验证幂等；声明式部分用 `winget configure test` 做无副作用检查；`%ProgramData%\CalmOS\devconfig-log.txt` 是排障第一现场。
6. **版本策略**：上游包版本"随 winget 当前发布走"，`Microsoft.DotNet.SDK.10`/`Python.Python.3.14` 只钉主版本（README Known limitations "Package versions move"）；Cascadia 字体 pin `2407.24` + SHA-256。个人 fork 想锁版本就要自己改这些点，且上游还没有 tag 可 pin，`-Ref` 只能钉 branch/SHA。
7. **关注机制迁移的方向**：CI 注释明说工作负载正从 winget-configure/DSC 模型迁往 PowerShell 原生引擎。若个人定制以声明式 YAML 为主体，应意识到这是上游正在淡出的路线（尽管 `winget configure` 本身仍是 Windows 的受支持功能）；若跟引擎走，则享受其重启续跑/签名校验等 DSC 路线没有的工程化能力。
